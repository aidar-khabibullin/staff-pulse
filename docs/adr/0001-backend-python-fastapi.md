# ADR 0001: Backend на Python/FastAPI вместо Node.js/Express

## Контекст

Фаза 1 реализовала mock API сервер на Node.js + Express + TypeScript (см. `e61514d`), что соответствовало формулировке задания «реализуйте собственный сервер» без жёсткой привязки к языку backend. Однако по условиям конкретного тестового задания backend-часть оценивается на Python/FastAPI — стек, отличный от изначально выбранного.

## Решение

Полностью переписать mock API сервер с Node.js/Express/TypeScript на Python 3 + FastAPI + uvicorn (`server/app/`), сохранив внешний контракт без изменений:

- `GET /api/org-tree` возвращает тот же плоский массив узлов с теми же полями и camelCase-именами (через pydantic alias, `server/app/models.py`);
- логика генерации мок-данных и проверки целостности `parentId` перенесена как есть;
- unit-тесты перенесены с Vitest на pytest (`server/tests/`), добавлен тест самого HTTP-эндпоинта через `TestClient`.

Frontend, e2e-тесты (`playwright.config.ts`) и остальная документация обновлены только в части команд запуска сервера (`uvicorn` вместо `npm run dev`), контракт API не менялся — фронтенд не заметил переезда backend.

## Альтернативы

- **Оставить Node.js/Express.** Отклонено: не соответствует требованию оценки backend-части именно на Python/FastAPI.
- **Держать оба сервера параллельно (Node как fallback).** Отклонено: дублирование логики генератора данных и двух наборов тестов ради временного соответствия только усложнило бы поддержку без практической пользы — единственный источник истины удобнее.
- **Переписать только эндпоинт, оставив Express-обвязку.** Не рассматривалось всерьёз: смешение двух рантаймов ради одного эндпоинта не даёт выигрыша, а FastAPI/uvicorn — не более сложная инфраструктура, чем Express.

## Последствия

- Backend теперь на Python 3.12+ (venv, `requirements-dev.txt`), что требует отдельного шага установки при локальном запуске без Docker (описано в README).
- WebSocket live-обновления (Фаза 5) реализованы сразу на FastAPI/`asyncio`, без миграции с Node — переезд состоялся до появления этой фичи.
- CI/Docker-конфигурация (`server/Dockerfile`) ориентируется на `pip install` и uvicorn, а не на `npm`/`node`.
