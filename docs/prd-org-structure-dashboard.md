# PRD: Org Structure Monitoring Dashboard

**Дата**: 2026-09-14
**Статус**: Draft

## Цель

Дать пользователю интерактивный дашборд для мониторинга иерархической орг-структуры компании (дивизионы → отделы → команды), позволяющий одновременно исследовать дерево подразделений и анализировать агрегированные показатели численности, бюджета и эффективности — с обновлением данных в реальном времени.

## Пользовательские сценарии

- Пользователь открывает дашборд -> видит дерево орг-структуры с раскрытым вторым уровнем, для каждого узла видны name, headcount и цветовой индикатор performance.
- Пользователь раскрывает/скрывает произвольную ветвь дерева -> дерево анимированно разворачивается/сворачивается, состояние сохраняется в рамках сессии.
- Пользователь переключается на табличный вид (или использует split-view на широком экране) -> видит аналитическую таблицу с суммарными показателями по каждому подразделению, включая всех потомков.
- Пользователь кликает по заголовку столбца таблицы -> строки сортируются по этому столбцу; двойной клик — сортировка в обратном порядке.
- Пользователь вводит текст в поле фильтра по названию -> таблица в реальном времени (с задержкой) сужается до совпадающих подразделений.
- Пользователь кликает по строке таблицы -> соответствующий узел выделяется в дереве.
- Пользователь наблюдает за дашбордом длительное время -> получает live-обновления показателей без перезагрузки страницы, изменённые ячейки временно подсвечиваются.
- Пользователь теряет соединение с сервером -> видит индикатор состояния соединения в шапке и автоматическое переподключение.
- Пользователь работает с клавиатуры -> может перемещаться по таблице (стрелки, Home/End, Enter) без использования мыши.
- Пользователь вводит запрос на естественном языке в поисковую строку (BONUS) -> получает отфильтрованный по смыслу запроса список подразделений либо обычный текстовый поиск как fallback.
- Пользователь запускает проект одной командой (в т.ч. через Docker) -> получает работающий клиент и сервер без ручной настройки, кроме `.env`.
- Пользователь (в т.ч. как читатель репозитория) хочет понять, где AI использовался в разработке -> находит раздел «AI в разработке» в README с описанием, что сгенерировано, что переписано руками и почему.

## В скоупе

- Собственный mock-сервер, отдающий `GET /api/org-tree` — плоский массив узлов `{ id, name, parentId, headcount, budget, performance, updatedAt }`, минимум 40 узлов, не менее 3 уровней вложенности.
- Клиентская валидация схемы ответа API; невалидный ответ обрабатывается как ошибка.
- Слой кэширования запросов (stale-while-revalidate или аналог) со stale time 5 секунд и инвалидацией только при реальном изменении данных.
- Интерактивное древовидное представление орг-структуры с раскрытием/скрытием ветвей и вторым уровнем, открытым по умолчанию.
- Обработка состояний загрузки, ошибки и пустого ответа для дерева и таблицы.
- Корректная отмена сетевых запросов при размонтировании компонентов.
- Аналитическая таблица с колонками: Подразделение, Уровень, Всего сотрудников, Бюджет суммарный, Средняя эффективность (взвешенная по headcount), с агрегацией по узлу и всем потомкам.
- Переключатель «Дерево / Таблица» либо совмещённый split-view на экранах ≥1280px.
- Сортировка таблицы по любому столбцу (прямая/обратная по двойному клику), real-time фильтр по названию с дебаунсом 250мс.
- Синхронизация выбора строки таблицы с выделением узла в дереве.
- Форматирование бюджетов вида `12 345 678 руб.`.
- Мемоизированный, однократный после загрузки данных расчёт агрегатов.
- Live-обновления данных (WebSocket, SSE или эффективный поллинг) с частичным патчем без полного рефетча, backoff при обрыве и индикатором соединения в шапке.
- Fade-out подсветка (~1.5с) обновлённых ячеек; пересчёт агрегатов только для затронутого узла и его предков.
- Клавиатурная навигация по таблице (стрелки, Home/End, Enter).
- Анимация раскрытия дерева через height transition с уважением `prefers-reduced-motion`.
- Docker-конфигурация (`docker-compose up`) для совместного запуска клиента и сервера, конфигурация через `.env`.
- Nginx-конфиг: проксирование API, отдача статики с gzip, production-сборка ≤200 КБ gzip.
- AI-поиск на естественном языке с преобразованием запроса в структурированный клиентский фильтр и текстовым fallback.
- Unit-тест на функцию агрегации показателей.
- Документация: `README` (запуск одной командой + раздел «AI в разработке»), `docs/architecture.md`, `docs/data-model.md`, ADR-записи для нетривиальных решений.
- Скриншоты или GIF финального результата.
- Каждый этап реализации фиксируется отдельным коммитом с тегом `step/N`.

## Не в скоупе

- Авторизация и управление доступом.
- Персистентное хранилище/БД — данные обслуживаются мок-сервером.
- Готовые UI-библиотеки компонентов (MUI, Ant Design и аналоги).
- Редактирование данных орг-структуры пользователем (только просмотр и анализ).
- Мультиязычность интерфейса.
- Мобильная адаптация как отдельная приоритетная цель (только соблюдение split-view порога ≥1280px).

## Технические ограничения

- Стек фиксирован: React, Vite, TypeScript; styled-components — опционально (плюс, не обязателен).
- Production-сборка клиента не должна превышать 200 КБ gzip.
- Никакого inline-CSS.
- Live-обновления обязаны применяться патчем, без полного повторного запроса дерева.
- Кэш должен инвалидироваться только при реальном изменении данных, а не по таймеру безусловно.
- Обязательно использование AI-инструментов (Claude, Cursor, Copilot и др.) в процессе разработки с задокументированным следом их применения.

## Критерии готовности

- [ ] `GET /api/org-tree` возвращает валидный плоский массив ≥40 узлов, ≥3 уровня вложенности; невалидная схема на клиенте трактуется как ошибка.
- [ ] Дерево раскрывается/скрывается по ветвям, второй уровень открыт по умолчанию; каждый узел отображает name, headcount и цветовой индикатор performance.
- [ ] Отображаются и корректно обрабатываются состояния: загрузка, ошибка, пустой ответ — без inline-CSS.
- [ ] Данные запрашиваются через кэширующий слой со stale time 5с; повторные обращения в пределах stale time не создают лишних сетевых запросов.
- [ ] Запросы корректно отменяются при размонтировании компонента (нет предупреждений/ошибок по обновлению состояния после unmount).
- [ ] Доступен переключатель «Дерево / Таблица» либо split-view на экранах ≥1280px.
- [ ] Таблица показывает столбцы Подразделение/Уровень/Всего сотрудников/Бюджет суммарный/Средняя эффективность с корректной агрегацией по потомкам и взвешенной по headcount эффективностью.
- [ ] Сортировка работает по каждому столбцу; двойной клик по заголовку инвертирует сортировку.
- [ ] Фильтр по названию работает в реальном времени с дебаунсом ~250мс.
- [ ] Клик по строке таблицы выделяет соответствующий узел в дереве; бюджет форматируется как `12 345 678 руб.`.
- [ ] Агрегаты вычисляются один раз после загрузки данных и мемоизированы (повторный рендер не пересчитывает их без изменения входных данных).
- [ ] Реализован канал live-обновлений (WebSocket/SSE/поллинг) с частичным патчем данных без полного рефетча.
- [ ] Обновлённые ячейки таблицы подсвечиваются и гаснут (fade-out) за ~1.5с.
- [ ] После live-обновления агрегаты пересчитываются только для затронутого узла и его предков (не для всего дерева).
- [ ] В шапке отображается индикатор состояния соединения; при обрыве применяется экспоненциальный backoff и восстановление соединения.
- [ ] Таблица управляема с клавиатуры: стрелки перемещают фокус, Home/End — к началу/концу, Enter — действие по строке.
- [ ] Раскрытие дерева анимировано через height transition; при `prefers-reduced-motion: reduce` анимация отключается/упрощается.
- [ ] `docker-compose up` поднимает клиент и сервер целиком; конфигурация читается из `.env`.
- [ ] Nginx проксирует API-запросы, отдаёт статику с gzip; production-сборка клиента ≤200 КБ gzip.
- [ ] AI-поиск принимает запрос на естественном языке и возвращает структурированный клиентский фильтр; при неуспехе используется текстовый fallback-поиск.
- [ ] Присутствует unit-тест на функцию агрегации показателей.
- [ ] README содержит инструкцию запуска одной командой и обязательный раздел «AI в разработке» (что сгенерировано, что переписано руками и почему).
- [ ] Присутствуют `docs/architecture.md`, `docs/data-model.md` и как минимум один ADR в `docs/adr/`.
- [ ] Приложены скриншоты или GIF финального результата.
- [ ] Каждый этап (01–04) закоммичен отдельно и помечен тегом `step/N`.
