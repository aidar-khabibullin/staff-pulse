# Plan: Org Structure Monitoring Dashboard

**PRD:** docs/prd-org-structure-dashboard.md
**Дата:** 2026-09-14

> Соответствие тегам коммитов из README (`step/N`): Фазы 1–3 → `step/1` (FOUNDATION), Фаза 4 → `step/2` (CORE), Фазы 5–6 → `step/3` (POLISH), Фазы 7–9 → `step/4` (BONUS).

> **E2E (Playwright):** тесты лежат в `e2e/*.spec.ts`, конфиг — `playwright.config.ts` в корне репозитория. Каждая фаза добавляет минимум один Playwright-тест, покрывающий её критерий готовности (`api` project — HTTP-контракты, `ui` project — браузерные сценарии, подключается в Фазе 2 вместе с `client/`). Запуск: `npm run test:e2e`.

## Фазы реализации

### Фаза 1: Mock API сервер (Tracer Bullet)

**Цель:** Минимальный рабочий путь — сервер отдаёт валидные данные орг-структуры, на которых строится всё остальное.
**Затрагивает:** backend
**Задачи:**

- [ ] Инициализировать backend-проект с эндпоинтом `GET /api/org-tree`
- [ ] Сгенерировать мок-данные: плоский массив ≥40 узлов, ≥3 уровня вложенности, поля `id, name, parentId, headcount, budget, performance (0–100), updatedAt`
- [ ] Базовая конфигурация запуска (порт, CORS для локальной разработки)
- [ ] Проверка внутренней целостности данных (каждый `parentId`, кроме корней, ссылается на существующий узел)
- [ ] Unit-тест на генератор мок-данных (количество узлов, глубина вложенности, обязательные поля)
- [x] Playwright `api`-тест: `GET /api/org-tree` — валидный массив ≥40 узлов, ≥3 уровня, обязательные поля (`e2e/org-tree.api.spec.ts`)

**Когда готова:** `curl GET /api/org-tree` возвращает валидный JSON-массив ≥40 узлов с ≥3 уровнями вложенности; тест генератора зелёный; Playwright `api`-тест зелёный.

### Фаза 2: Frontend scaffold и слой данных с кэшированием

**Цель:** Клиент умеет получать и валидировать данные орг-структуры через кэширующий слой, корректно обрабатывая загрузку/ошибку/пустой ответ.
**Затрагивает:** frontend
**Задачи:**

- [ ] Scaffold Vite + React + TypeScript, настроить абсолютные импорты
- [ ] Клиентская валидация схемы ответа API; невалидный ответ обрабатывается как ошибка
- [ ] Слой кэширования запроса (stale-while-revalidate или аналог) со stale time 5 секунд
- [ ] Состояния загрузки, ошибки и пустого ответа (без inline-CSS)
- [ ] Отмена запроса при размонтировании компонента
- [ ] Подключить `ui` project в `playwright.config.ts` (webServer для `client/`, `baseURL: http://localhost:5173`)
- [ ] Playwright `ui`-тест: приложение загружается, отображает данные после успешного запроса к `/api/org-tree`

**Когда готова:** Приложение запрашивает `/api/org-tree` через кэш-слой; повторный запрос в пределах 5с не создаёт нового обращения к сети; для каждого состояния (loading/error/empty) есть видимый UI; тест на отмену запроса при unmount проходит; Playwright `ui`-тест загрузки данных зелёный.

### Фаза 3: Интерактивное дерево орг-структуры

**Цель:** Пользователь может визуально исследовать иерархию подразделений.
**Затрагивает:** frontend
**Задачи:**

- [ ] Построение иерархии из плоского массива (дивизионы → отделы → команды)
- [ ] Раскрытие/скрытие ветвей; второй уровень открыт по умолчанию
- [ ] Отображение на узле `name`, `headcount` и цветового индикатора `performance`
- [ ] Стилизация компонента дерева без inline-CSS
- [ ] Unit/component-тест: корректное построение дерева из плоского списка и переключение раскрытия узла
- [ ] Playwright `ui`-тест: клик по узлу раскрывает/скрывает потомков; второй уровень открыт по умолчанию

**Когда готова:** Дерево отображается с открытым вторым уровнем; клик по узлу раскрывает/скрывает его потомков; тесты построения иерархии и toggle проходят; Playwright `ui`-тест раскрытия дерева зелёный.

### Фаза 4: Аналитическая таблица и агрегация

**Цель:** Пользователь видит агрегированные показатели по подразделениям и может их сортировать/фильтровать, синхронно с деревом.
**Затрагивает:** frontend
**Задачи:**

- [ ] Функция агрегации (сумма headcount/budget, средняя performance взвешенная по headcount) для узла и всех потомков, с мемоизацией; unit-тест на функцию агрегации
- [ ] Табличный компонент со столбцами: Подразделение, Уровень, Всего сотрудников, Бюджет суммарный, Средняя эффективность; форматирование бюджета как `12 345 678 руб.`
- [ ] Сортировка по любому столбцу; двойной клик по заголовку — обратная сортировка
- [ ] Фильтр по названию в реальном времени с дебаунсом 250мс; переключатель «Дерево / Таблица» (или split-view ≥1280px)
- [ ] Синхронизация: клик по строке таблицы выделяет соответствующий узел в дереве
- [ ] Playwright `ui`-тест: сортировка по столбцу, фильтр по названию, клик по строке выделяет узел дерева

**Когда готова:** Таблица показывает верно агрегированные и отформатированные значения; сортировка и фильтр работают согласно требованиям; выбор строки подсвечивает узел дерева; тест агрегации проходит и агрегаты не пересчитываются на каждый рендер без изменения входных данных; Playwright `ui`-тест таблицы зелёный.

### Фаза 5: Live-обновления на сервере

**Цель:** Сервер способен рассылать изменения показателей орг-структуры в реальном времени.
**Затрагивает:** backend
**Задачи:**

- [ ] Механизм live-обновлений (WebSocket или SSE) на сервере
- [ ] Логика периодической генерации изменений показателей узлов для демонстрации
- [ ] Контракт патч-сообщения (структура: id узла, изменённые поля, updatedAt) задокументирован
- [ ] Обработка подключения/отключения клиентов без падения сервера
- [ ] Тест на корректность формата и содержимого патч-сообщения
- [ ] Playwright `api`-тест: подключение к live-каналу и получение хотя бы одного корректного патч-сообщения

**Когда готова:** Подключённый клиент (например, через websocat/тестовый скрипт) получает корректно сформированные патч-сообщения при изменении данных на сервере; Playwright `api`-тест live-канала зелёный.

### Фаза 6: Live-обновления и UX на клиенте

**Цель:** Изменения с сервера отражаются в интерфейсе без полного рефетча, с визуальной обратной связью и устойчивостью соединения.
**Затрагивает:** frontend
**Задачи:**

- [ ] Подключение к каналу live-обновлений (WebSocket/SSE/поллинг) и применение патча к данным без полного рефетча
- [ ] Пересчёт агрегатов только для затронутого узла и его предков
- [ ] Fade-out подсветка обновлённых ячеек (~1.5с); индикатор состояния соединения в шапке; экспоненциальный backoff при обрыве
- [ ] Keyboard navigation по таблице (стрелки, Home/End, Enter) и анимация раскрытия дерева через height transition с учётом `prefers-reduced-motion`
- [ ] Тест на применение патча и корректный частичный пересчёт агрегатов (затронутый узел + предки, остальные не трогаются)
- [ ] Playwright `ui`-тест: клавиатурная навигация по таблице (стрелки, Home/End, Enter); индикатор соединения меняет состояние

**Когда готова:** Изменение данных на сервере отражается в UI без полного рефетча дерева; обновлённые ячейки временно подсвечиваются; при обрыве соединения индикатор меняется и происходит переподключение с backoff; клавиатурная навигация работает; тест частичного пересчёта агрегатов проходит; Playwright `ui`-тест keyboard navigation и индикатора соединения зелёный.

### Фаза 7: Production-сборка и Docker

**Цель:** Проект поднимается одной командой в контейнерах и соответствует ограничению на размер production-сборки.
**Затрагивает:** backend, frontend
**Задачи:**

- [ ] Dockerfile для клиента и сервера, `docker-compose.yml`, конфигурация через `.env`
- [ ] Nginx: проксирование `/api` на сервер, отдача статики с gzip
- [ ] Оптимизация production-сборки клиента (минимизация/разделение кода) до ≤200 КБ gzip
- [ ] Скрипт/проверка размера итоговой сборки в CI-подобном виде
- [ ] Smoke-тест: `docker-compose up` поднимает клиент и сервер, `/api/org-tree` доступен через Nginx
- [ ] Playwright `ui`-тест против `docker-compose`-стенда (baseURL на Nginx-порт): приложение открывается и показывает дерево

**Когда готова:** `docker-compose up` из чистого состояния поднимает работающее приложение по конфигурации из `.env`; production bundle клиента ≤200 КБ gzip; smoke-тест проходит; Playwright-тест против Docker-стенда зелёный.

### Фаза 8: AI-поиск на естественном языке

**Цель:** Пользователь может искать подразделения запросом на естественном языке с надёжным fallback.
**Затрагивает:** frontend
**Задачи:**

- [ ] Поле поиска на естественном языке в UI
- [ ] Преобразование запроса в структурированный клиентский фильтр (по показателям/названию/уровню)
- [ ] Применение структурированного фильтра к дереву и таблице
- [ ] Fallback на обычный текстовый поиск при ошибке/неуспехе разбора запроса
- [ ] Тест на fallback-сценарий (некорректный/пустой AI-ответ → текстовый поиск)
- [ ] Playwright `ui`-тест: ввод запроса на естественном языке применяет фильтр; сценарий fallback на текстовый поиск

**Когда готова:** Запрос на естественном языке приводит к применению соответствующего фильтра; при сбое AI-разбора работает текстовый поиск как fallback; тест fallback-сценария проходит; Playwright `ui`-тест AI-поиска зелёный.
